# Design Specification: Booking Conflict and Cancellation

## 1. Scope and service boundary

The service owns one responsibility: deciding whether an appointment can be booked for a provider without breaking the no-overlap rule, and recording cancellations. It exposes a Python API (`AppointmentService`) and a thin CLI adapter (`scheduler.cli`). The CLI only parses input and formats output; it contains no business logic.

Out of scope: provider and patient management, availability or working hours, recurring slots, notifications, authentication, persistence beyond process memory, and any UI.

## 2. Data model

| Field         | Type                         | Notes                                        |
|---------------|------------------------------|----------------------------------------------|
| `id`          | `str` (UUID4)                | Generated by the service                     |
| `provider_id` | `str`                        | Required, non-blank; surrounding whitespace trimmed |
| `start`       | `datetime`, timezone-aware UTC | Inclusive                                   |
| `end`         | `datetime`, timezone-aware UTC | Exclusive; must be after `start`            |
| `status`      | `ACTIVE` or `CANCELLED`      | Cancellation is a soft delete                |

`Appointment` is an immutable dataclass. Cancelling replaces the stored record with a copy whose status is `CANCELLED`, so a caller holding an earlier reference never sees it change underneath them.

Storage is two dictionaries:

- `_by_id`: appointment ID → appointment
- `_by_provider`: provider ID → list of that provider's appointment IDs

The conflict check only scans the requesting provider's appointments.

## 3. API

| Operation | Input | Success | Failure |
|---|---|---|---|
| `book(provider_id, start, end)` | ISO-8601 string ending in `Z` or `+00:00`, or an aware UTC `datetime` | returns `Appointment` | `ValidationError` (`INVALID_INPUT`); `ConflictError` (`CONFLICT`, with `conflicting_id`) |
| `cancel(appointment_id)` | `str` | `CancelResult(CANCELLED, appt)` | `CancelResult(NOT_FOUND)`; `CancelResult(ALREADY_CANCELLED, appt)`; `ValidationError` if the ID is blank |
| `get(appointment_id)` | `str` | `Appointment` or `None` | none |
| `list_for_provider(provider_id, include_cancelled=False)` | `str` | list sorted by `start` | none |

Design choice: invalid input and conflicts raise exceptions, because the caller made an error. Cancelling a missing or already-cancelled appointment returns a result value instead, because it is an expected business outcome and the criteria ask for "a clear result". It also makes cancel safe to retry.

## 4. Booking invariant

> For every provider `p`, and for any two distinct ACTIVE appointments `a` and `b` of `p`: `a.end <= b.start` or `b.end <= a.start`.

Intervals are half-open: `[start, end)`. Two intervals overlap when `a.start < b.end and b.start < a.end`. Using strict `<` is what allows back-to-back appointments, where one ends exactly when the next starts. Cancelled appointments are left out of the check, so cancelling frees the time.

## 5. Validation order and atomicity

1. Validate the provider ID, both timestamps, and that `end > start`, **before** taking the lock or touching any stored data.
2. Take the lock, run the conflict scan, then insert.

A rejected request therefore never changes stored bookings (criterion 5). The tests check this by comparing a snapshot of the store before and after every invalid request.

## 6. Concurrency approach

One `threading.Lock` per service instance covers:

- the whole check-then-insert step in `book`
- the read-modify-write step in `cancel`
- reads in `get` and `list_for_provider`

Without the lock, two threads could both pass the conflict check for the same slot and both insert, which is a race between checking and acting. One global lock is the simplest choice that is clearly correct, and contention is not a concern at this scale. A lock per provider would allow more parallel work but adds complexity that isn't needed here.

The tests cover this:

- 50 threads book the same slot at the same moment, and exactly one succeeds.
- 40 threads book overlapping ranges, and afterwards no two active appointments overlap.

Mutation check: removing the lock and adding a 1 ms delay makes both tests fail, so they really detect the race.

**If this were moved to a database:** enforce the same rule in the database itself, not only in application code. For example, use a PostgreSQL exclusion constraint:

```sql
EXCLUDE USING gist (provider_id WITH =, tstzrange(start_at, end_at, '[)') WITH &&) WHERE (status = 'ACTIVE')
```

Alternatively, lock the provider's row with `SELECT ... FOR UPDATE` inside a transaction before checking.

## 7. Time handling

All timestamps must carry an explicit UTC offset (`Z` or `+00:00`):

- Timestamps with no offset are **rejected**, not assumed to be UTC. A missing offset usually means the client made a mistake, and silently treating local time as UTC would book the wrong slot.
- Timestamps with a non-zero offset (for example `+05:30`) are also rejected. The assessment limits the work to UTC, and rejecting is easy to relax later; quietly converting would be harder to undo.
- Microsecond precision is kept, so an overlap of one microsecond is still a conflict (this is tested).

## 8. Tradeoffs

| Decision | Alternative | Why |
|---|---|---|
| Linear scan of one provider's appointments | Interval tree or sorted list with bisect | Each provider has few bookings in this scope. A scan is O(n) per booking but obviously correct. |
| Keep cancelled records (soft delete) | Delete them | Keeps an audit trail and lets a repeat cancel return `ALREADY_CANCELLED` instead of `NOT_FOUND`. |
| One global lock | Lock per provider | Simpler and clearly correct; throughput is not a goal here. |
| Reject non-UTC offsets | Convert them to UTC | Strict reading of the UTC-only rule; easy to relax later. |
